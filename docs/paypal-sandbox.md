# PayPal para la tienda de Gimae

## Arquitectura y archivos

- `dist/index.html` y `dist/app.js`: portada de Merch, enlaza a `shop.html`; no checkout aquí.
- `dist/content.js`: activa PayPal solo tras configurar Sandbox; no incluye PayPal Client ID ni tasa manual.
- `dist/shop.html`, `dist/shop.js`, `dist/styles.css`: carrito existente, modales nativos, vista de espera cuando se abre PayPal, resumen que consulta el estado del webhook y SDK oficial `https://www.paypal.com/sdk/js`. La referencia del intento se guarda en el dispositivo antes de abrir PayPal para poder recuperarlo tras un corte de conexión. El indicador respeta `prefers-reduced-motion`.
- `dist/backend.js`, `dist/supabase-config.js`: catálogo Supabase y URL/publishable key públicas existentes.
- `supabase/migrations/*_paypal_orders.sql`: pedidos privados, instantáneas del tipo de cambio y deduplicación de webhooks.
- `supabase/functions/{paypal-create-order,paypal-capture-order,paypal-order-status,paypal-webhook,paypal-reconcile}` y `_shared/paypal.ts`: pagos, consulta de estado, verificación y conciliación.
- `supabase/config.toml`: funciones públicas sin JWT Supabase; la autorización de PayPal ocurre por OAuth y firma de webhook. Crear/capturar tienen validación de payload, origen permitido y límites operativos; Origin no sustituye un límite de solicitudes.

## Credenciales y moneda

El SDK de PayPal necesita el Client ID en el navegador. Se guarda en un secret de Edge Functions y se devuelve al comprador al preparar la orden; **no es secreto confidencial**. El Client Secret, token BDE y Supabase secret/service role jamás se envían al navegador. La URL y publishable key Supabase actuales son públicas por diseño. Asegura que el Client ID y Client Secret pertenezcan a la misma app y que su merchant ID sea el de la cuenta receptora.

La fuente del monto CLP son `public.products`/`public.product_variants`, jamás el carrito ni `content.js`. La función consulta la serie oficial `F073.TCO.PRE.Z.D` (dólar observado CLP/USD) del Banco Central, conserva cache hasta 12 horas y exige una observación de menos de cinco días. Redondea una vez el total a centavos USD y guarda el precio CLP, tasa, fecha y total USD. Si la API falla y no hay cache vigente, no permite cobrar. La tasa oficial no es la tasa de conversión final de PayPal ni incluye sus comisiones. Se informa al cliente el monto exacto en USD antes de abrir PayPal. El checkout solo admite `pickup`: no se pide dirección ni se cobra envío. Para habilitar despacho pagado hará falta definir antes zonas y tarifas, almacenarlas en servidor y sumarlas a la orden.

## Antes del despliegue

1. Crea una app REST de **Sandbox** en el [PayPal Developer Dashboard](https://developer.paypal.com/dashboard/applications/sandbox). Identifica Client ID, Client Secret y Merchant ID de la cuenta business Sandbox. Crea también una cuenta buyer Sandbox.
2. Obtén un token de la [API BDE del Banco Central](https://si3.bcentral.cl/estadisticas/Principal1/Web_Services/acceso_api.html). Guárdalo de forma privada; caduca según la configuración de esa API.
3. En el proyecto Supabase de pruebas, aplica en orden las migraciones existentes y la nueva (`npx supabase db push` tras `npx supabase link --project-ref <REF_DE_PRUEBA>`). No ejecutes este paso sobre producción antes de probar y revisar el SQL.
4. Configura las variables desde una terminal privada, **sin valores literales en el historial del shell ni en el repo**. Por ejemplo, usa `npx supabase secrets set --env-file <RUTA_PRIVADA>`; ese archivo debe quedar fuera del repositorio. Variables: `PAYPAL_ENV=sandbox`, `PAYPAL_CLIENT_ID`, `PAYPAL_CLIENT_SECRET`, `PAYPAL_MERCHANT_ID`, `PAYPAL_WEBHOOK_ID`, `BCCH_API_TOKEN`, `PAYPAL_ALLOWED_ORIGINS=https://nachodev-ui.github.io,http://localhost:8000`. La URL y la secret key Supabase son inyectadas por la plataforma; el código acepta `SUPABASE_SECRET_KEYS.default` o la legacy `SUPABASE_SERVICE_ROLE_KEY`. El origen de GitHub Pages no incluye `/gimae-web/`.
5. Despliega `paypal-create-order`, `paypal-capture-order`, `paypal-order-status`, `paypal-webhook` y `paypal-reconcile` mediante `npx supabase functions deploy <nombre>` desde la raíz del repo. La configuración `verify_jwt=false` permite webhooks y solicitudes públicas; `paypal-reconcile` comprueba además una credencial interna aleatoria almacenada en Vault. La consulta pública de estado requiere el UUID del pedido junto con el ID PayPal y solo devuelve el estado, sin datos personales.
6. Registra en la app Sandbox el webhook `https://<REF_DE_PRUEBA>.supabase.co/functions/v1/paypal-webhook` para `PAYMENT.CAPTURE.COMPLETED` y `CHECKOUT.ORDER.APPROVED`. Si ya existe el webhook, edita sus eventos y agrega el segundo sin crear otra URL ni cambiar el Webhook ID. La función comprueba la firma y la orden PayPal antes de capturar una aprobación, incluso si el navegador se desconectó. Copia el **Webhook ID** emitido por PayPal a `PAYPAL_WEBHOOK_ID`, que no es el Client ID.
7. En la base de pruebas confirma stock y un número positivo para una variante o producto. El seed deja todos los inventarios en cero y `stock_confirmed=false`, por lo que ninguna compra pasará sin este paso. En `dist/content.js`, cambia `PAYMENT_METHODS.paypal.enabled` a `true`; apunta `dist/supabase-config.js` al proyecto **de pruebas** si vas a ensayar desde el frontend. No publiques este ajuste en la rama de producción durante Sandbox.

### Conciliación sin navegador

- La migración `paypal_reconciliation` crea un token aleatorio en Vault y guarda solo su hash en una tabla privada. Activa `pg_cron` y `pg_net`; el programador se configura por proyecto después de desplegar la función. En el proyecto Sandbox `hvaonobbpzbupanuymkh`, ejecutar `supabase/scripts/schedule-paypal-reconcile-sandbox.sql` una vez. Para otro proyecto, **cambia la URL** de ese script antes de programarlo; no copies la tarea Sandbox a Live.
- Cada dos minutos se examinan hasta ocho pedidos vencidos para revisión. La función obtiene su estado de la API PayPal y solo marca `paid` si una captura ya completada coincide en orden, comercio, referencia, moneda e importe. Si PayPal ya no encuentra la orden pero el servidor guardó el ID de captura, consulta la captura directamente. No inicia una captura nueva. Una orden aprobada sin captura conserva `awaiting_approval` y registra `PAYPAL_APPROVED_NOT_CAPTURED` para revisión; el webhook `CHECKOUT.ORDER.APPROVED` y el retorno del comprador siguen siendo los mecanismos que capturan la aprobación. Una orden caducada/no encontrada registra `PAYPAL_ORDER_NOT_FOUND` y se vuelve a revisar con menor frecuencia; su cierre definitivo corresponde a la etapa de pedidos abandonados.
- Revisa la tarea en `cron.job` y `cron.job_run_details`, las respuestas HTTP en `net._http_response`, y `merch_orders.last_reconciled_at`, `reconcile_attempts` y `reconcile_error`. La reconciliación no crea eventos ficticios en `paypal_webhook_events`. Los intentos sin pago se espacian para evitar llamadas indefinidas cada dos minutos.

## Pruebas de Sandbox

- `python3 -m http.server 8000 --directory dist`; abre `http://localhost:8000/shop.html?paypal-sandbox=1` (cualquier `localhost` distinto debe añadirse a `PAYPAL_ALLOWED_ORIGINS`). Agrega la variante confirmada, selecciona **Retiro**, completa nombre y contacto, prepara PayPal y verifica total CLP y monto USD. La fecha y tasa utilizadas quedan registradas en el pedido del servidor.
- Inicia sesión en el popup con el buyer Sandbox. La tienda muestra una vista de espera mientras el popup está abierto y consulta el estado del pedido mientras el resumen siga abierto; tras los primeros 30 segundos reduce la frecuencia de consultas. Al recuperar la conexión, una vista de error por resultado incierto abre el resumen automáticamente; si el resumen ya está abierto o el comprador vuelve a la pestaña, consulta de inmediato. La tarjeta de pedido reciente también sigue comprobando el estado a intervalos mientras la tienda esté visible. «Consultar confirmación» queda disponible como alternativa manual. Comprueba `merch_orders.status`: tras `capture` puede estar `capture_pending`; el webhook firmado o la consulta directa a PayPal desde el conciliador lo cambian a `paid` y establecen `paid_at`. Verifica que el `paypal_capture_id`, el monto USD y el Merchant ID correspondan al panel PayPal Sandbox. El resumen solo indica pago confirmado cuando el servidor responde `paid`.
- Cancela otro checkout. El carrito debe permanecer y no debe haber un pedido `paid`. Desde `http://localhost:8000/shop.html?paypal-sandbox=1&paypal-test-error=1`, prepara otro pago: se simula localmente el callback `onError` del SDK sin abrir PayPal ni cobrar. Debe aparecer el error y conservarse el carrito; sal de esa URL antes de hacer una compra normal. Se crea un intento Sandbox en la base, pero no un pago. Simula una API BDE no disponible o stock agotado; la creación debe fallar sin ofrecer el botón de PayPal.
- Para ensayar una desconexión sin aprobar nada, prepara una orden Sandbox con la URL normal, deja el popup abierto, desconecta la red y recarga la tienda. Al volver la red, reabre «Tu pedido»: debe mostrar «Pago sin confirmar», conservar el ID de PayPal y ofrecer «Comprobar y completar si aprobaste en PayPal». Si no aprobaste, esa opción no podrá capturar y deberás empezar una compra nueva. Si ya aprobaste, el webhook firmado `CHECKOUT.ORDER.APPROVED` permite capturar desde el servidor aunque no vuelvas al navegador; el botón de recuperación usa la misma `PayPal-Request-Id` para evitar duplicados. Después, `PAYMENT.CAPTURE.COMPLETED` marca el pedido como `paid` y las consultas reflejan ese estado.
- Prueba un POST sin firma a `paypal-webhook`: debe devolver 400/401 y no modificar pedidos. Un `PAYMENT.CAPTURE.COMPLETED` legítimo debe registrarse una sola vez aunque PayPal reenvíe el evento. El simulador de PayPal emite eventos ficticios que no están ligados a tus pedidos reales; úsalo para probar la recepción, no para simular una compra completada de verdad.
- Desde el cliente público, intenta `select`, `insert`, `update` y `delete` en `merch_orders`, `paypal_fx_rates` y `paypal_webhook_events`. No debe poder leer ni escribir. Con sesión admin, `merch_orders` permite SELECT y deniega escritura directa. Verifica en la base que cambiar montos, cantidades o IDs enviados por el cliente no altere los precios calculados en servidor.

## Publicación y operación

Repite en Live con una app y webhook **Live** separados, `PAYPAL_ENV=live`, secrets Live y un proyecto Supabase o configuración de producción apropiada. Configura allí la tarea Cron con la URL Live y verifica su primera ejecución. Confirma el inventario real antes de activar `PAYMENT_METHODS.paypal.enabled`; no se reservan unidades mientras el comprador tiene abierta la ventana de PayPal, por lo que el equipo debe vigilar ventas simultáneas. Configura límites de solicitudes al endpoint público y alertas sobre errores de funciones/webhook y conciliación. Si una orden aparece aprobada pero sin captura, examina `reconcile_error` antes de volver a cobrar. Reembolsos y contracargos requieren un procedimiento de revisión aparte. Informa en la política de privacidad el almacenamiento de nombre/contacto en Supabase y define un período de conservación.
